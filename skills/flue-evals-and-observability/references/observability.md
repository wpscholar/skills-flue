# Observability in Flue

Live source: `flue docs read guide/observability` · `flue docs read reference/events`

## Two event surfaces

- **Conversation stream** (product surface) — one conversation's durable, render-ready messages, data parts, and settlements. Consumed over HTTP with `createFlueClient(...)`'s `observe()` / `history()`.
- **Runtime event stream** (operational surface) — live activity across every agent in the process: model requests, tool executions, logs, token counts. Consumed **in-process** with `observe()` from `@flue/runtime`.

Both are named `observe()` and have fundamentally different shapes. Telemetry, metering, and error reporting belong on the runtime stream. They share correlation identifiers — a conversation message's `submissionId` matches the runtime events its submission produced.

## Subscribing

```ts
// src/app.ts — module top level
import { observe } from '@flue/runtime';

observe((event) => {
  if (event.type === 'submission_settled' && event.outcome === 'failed') {
    console.error(`[${event.agentName}] submission ${event.submissionId} failed:`, event.error?.message);
  }
});
```

1. **Stay cheap.** Subscribers run synchronously on the emission path. Branch on `event.type`, return early, queue substantial async work rather than blocking emission.
2. **Treat events as read-only.** Each delivery is a detached, frozen observation.
3. **Failures are contained.** A throwing subscriber is logged and skipped — it never halts the agent or other subscribers. Returned promises are observed for rejection but not awaited.

Scope: the subscription is **isolate-scoped and live-only** — no durable replay, no cross-process aggregation. On Node, one process hosts all agents, so one registration sees everything. **On Cloudflare each agent conversation runs in its own DO isolate**, so a subscriber registered from `app.ts` runs in each isolate and observes only that isolate's activity. `flue run` never loads `app.ts` — register in the agent module when a subscriber must also run under the CLI.

## What the stream contains

Every event carries the event-format version, a per-context `eventIndex`, a `timestamp`, and applicable correlation fields: `agentName`, `conversationId`, `instanceId`, `submissionId`, `operationId`, `turnId`, `taskId`.

| Events | Activity |
|---|---|
| `agent_start`, `agent_end`, `idle` | Agent loop lifecycle |
| `submission_settled` | A durable submission reached `completed`, `failed`, or `aborted` — **the reliable terminal signal** |
| `operation_start`, `operation` | Prompt, skill, task, shell, and compact operation boundaries, with duration and rolled-up usage |
| `turn_start`, `turn_request`, `turn`, `turn_messages` | Model turns |
| `message_*`, `text_delta`, `thinking_*` | Live message and reasoning progress |
| `tool_start`, `tool` | Tool execution, correlated by `toolCallId` |
| `task_start`, `task` | Subagent delegation, with result, error state, and duration |
| `compaction_start`, `compaction` | Context compaction, with message counts and usage |
| `log` | Structured logs written by tools and hooks |

**Streaming deltas signal live progress, not authoritative message state** — the assistant `message_end` event carries the completed message. **Nested errors do not necessarily fail containing work** (an agent can recover from a failed turn or tool call), so alert on `submission_settled` outcomes and read nested `isError` events as diagnostic context only.

Two live-only properties: live observations carry extra detail via `FlueObservation` — normalized tool arguments, effective results, classified `errorInfo` including throw-site stacks — never persisted or replayed. And **`turn_request` exists in-process only**, containing the full model-visible request (provider identity, settings, system prompt, messages, tools); it is delivered to `observe()` subscribers and never persisted or served over HTTP.

## Token usage and cost

| `usage` field | Meaning |
|---|---|
| `input`, `output` | Tokens sent to and generated by the model |
| `cacheRead`, `cacheWrite` | Prompt-cache tokens read and written |
| `totalTokens` | Total across all components |
| `cost` | Estimated cost from the model catalog's rates, per component plus `total` |

```ts
observe((event) => {
  if (event.type !== 'turn' || !event.response.usage) return;
  const { usage } = event.response;
  metrics.increment('llm.tokens', usage.totalTokens, {
    agent: event.agentName,
    model: event.request.requestedModel,
    purpose: event.purpose, // 'agent' | 'compaction' | 'compaction_prefix'
  });
  metrics.increment('llm.cost', usage.cost.total, { agent: event.agentName });
});
```

**Double-counting gotcha:** usage rolls up at coarser boundaries — `operation` and `compaction` events carry aggregate usage. When summing across events, **sum one level only**: `turn` values are the leaves, and roll-ups already include them. Durations at different levels overlap the same way and should not be added together.

Inside the agent, `useResponseFinish()` receives the whole response's aggregate usage — the right place to stamp token counts onto response metadata for your client.

## Provider diagnostics

A `turn` event's `response` is normalized (`finishReason`, `error` use Flue's vocabulary). Allowlisted raw provider metadata rides alongside when present:

- `providerFinishReason` — the provider's exact finish value before normalization
- `gatewayLogId` — the response's Cloudflare AI Gateway log id (`cf-aig-log-id`)

Both are telemetry only and never affect execution or replay. Only the Workers AI provider attaches both today.

```ts
observe((event) => {
  if (event.type !== 'turn' || !event.isError) return;
  console.error('model turn failed', {
    provider: event.request.providerName,
    model: event.request.requestedModel,
    finishReason: event.response.finishReason,
    providerFinishReason: event.response.providerFinishReason,
    gatewayLogId: event.response.gatewayLogId,
    error: event.response.error?.message,
  });
});
```

`request.providerId` is the registration key from the model specifier; `request.providerName` is the semantic provider identity — **they differ when a gateway or custom registration fronts the model.**

## Tool activity and logs

`tool_start` / `tool` carry tool name, `toolCallId`, duration, error state, and result — for both model-driven calls and programmatic shell activity.

```ts
async run({ data, log }) {
  log.info('sync started', { records: data.ids.length });
  const failed = await crm.sync(data.ids);
  if (failed.length > 0) log.error('sync incomplete', { failed: failed.length });
  return { output: { synced: data.ids.length - failed.length } };
}
```

Lifecycle hook contexts such as `useAgentStart` carry the same `log` interface. Tool logs are stamped with `tool` and `toolCallId`; hook logs with the hook that wrote them.

**The model never sees log lines.** They are runtime events, not conversation content — they never appear in rendered client messages and reach only in-process subscribers. Forward them yourself:

```ts
observe((event) => {
  if (event.type !== 'log') return;
  logger.log(event.level, event.message, { ...event.attributes, conversation: event.conversationId });
});
```

## Providers

- **Sentry** — terminal failures as issues, every log in Sentry Logs, optional AI traces with content off by default. `flue add tooling sentry`
- **Braintrust** — LLM tracing: operations as traces with model, tool, task, and compaction spans plus usage. `flue add tooling braintrust`
- **OpenTelemetry** — standards-based GenAI spans, metrics, and logs.

```ts
import { createOpenTelemetryInstrumentation } from '@flue/opentelemetry';
import { instrument } from '@flue/runtime';

instrument(createOpenTelemetryInstrumentation());
```

Span-producing integrations register through `instrument(...)`, which pairs an observer with an execution interceptor so spans wrap live agent, model, tool, and task execution. They compose — an error reporter and a tracer can subscribe side by side.

## Cloudflare

Agent work is visible to the platform's own observability with no Flue-side wiring: admission answers immediately, then the response executes start-to-settlement as a **single invocation**. Workers Logs attributes tool and hook logs to the response that wrote them; Workers Traces captures one trace per response with model calls and other subrequests as spans. Both are enabled in `wrangler.jsonc`.

`createCloudflareTracing()` is installed by default. Install it yourself **only to customize** the content policy, and only at `app.ts` module scope — an explicit install registers ahead of the default and replaces it, and a **post-startup install throws** because the registration slot is taken. `tracing: false` in `flue.config.ts` removes agent tracing from the build.

```ts
instrument(createCloudflareTracing({ content: false }));
```

Spans per response: `invoke_agent {agent}` (the whole run; `gen_ai.agent.name`, `gen_ai.agent.id`, `gen_ai.conversation.id`, aggregate `gen_ai.usage.*`), `chat {model}` (one per model turn including compaction turns, with provider `fetch` subrequests nested inside), and `execute_tool {tool}` (one per tool call). Subagent task runs appear as nested `invoke_agent` spans. Names and attributes follow OpenTelemetry GenAI conventions; Flue-specific keys live under `flue.*`.

**Content budget:** a **56 KiB per-span** budget is enforced in-band across all content attributes sharing one pool. Token usage, finish, and error attributes must always land, and a reserve keeps room for output messages beside large prompts. Payloads stay valid JSON; oldest messages drop first behind a `role: "flue"` sentinel; oversized strings are cut with a `[flue:truncated, N more bytes]` suffix. **Search for `[flue]` in the dashboard to find truncated content.** `truncateContent` from `@flue/runtime/telemetry` exports the same algorithm.

Two exclusions hold on this backend regardless of policy: raw error messages and stack traces never ship (failed spans record only low-cardinality `error.type`; aborted work is marked `flue.canceled` rather than counted as error), and caller-origin shell (`bash`) operations stay content-free.

## Protecting sensitive content

Runtime events can contain prompts, system instructions, reasoning, tool arguments and results, and error details — and **both trace adapters capture conversation content by default.**

> For every exporter that leaves Cloudflare, installing an instrumentation with `instrument(...)` **is** the consent: nothing is emitted by merely deploying, but once that line exists, prompts and tool payloads flow to the receiving backend.

Cloudflare's own Workers Traces is the exception — the switch there is enabling traces on the account, and content stays within it.

Every adapter takes the same two controls:

```ts
instrument(
  createCloudflareTracing({
    content: {
      transform(content, scope) {
        if (scope.contentType === 'tool_result') return undefined; // omit entirely
        return scrubPII(content);
      },
    },
  }),
);
```

The transform runs on a detached copy; returning `undefined` omits that content; a throwing transform emits a `[flue]` failure sentinel.

Two unconditional protections: **`turn_request` events never leave the process**, and image content blocks never carry raw bytes — their `data` is replaced with an `IMAGE_DATA_OMITTED` sentinel.

Per-exporter posture differs:

| Exporter | Posture |
|---|---|
| Cloudflare adapter | Never emits raw error messages or stacks |
| OpenTelemetry adapter | Passes exception messages and stack traces through the same content gate |
| Sentry integration | Keeps model and tool content out of traces unless its record flags opt in |
| Braintrust | Content-bearing, with a masking hook |

Review the retention and access controls of whatever receives your traces, and make the data-handling decision explicitly.
